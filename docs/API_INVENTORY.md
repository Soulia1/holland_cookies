# API Inventory — Holland Cookie

Every HTTP endpoint the server exposes. Generated by reading `backend/server.js`
and the four routers it mounts; there are no dynamically registered routes.

**36 endpoints.** Anything not listed here returns `404 {"error":"NOT_FOUND"}`
from the `/api` catch-all, and any method outside
`GET/HEAD/POST/PATCH/DELETE/OPTIONS` returns `405` before routing.

## How to read the Auth column

| Value | Meaning |
|---|---|
| **PUBLIC** | No credential. Still subject to origin checking on writes and to a rate-limit class. |
| **ADMIN** | Requires a valid `holland_admin_session` cookie. Enforced by `requireAdmin`, independently, on every route — never by the dashboard hiding a button. |
| **CUSTOMER** | Requires a valid `holland_customer_session` cookie from a proved email. |

**Firestore rules protect none of these.** The server uses the Admin SDK, which
bypasses rules entirely. Authorization is enforced here or nowhere.

## Global middleware, applied before any route

Applied in `backend/server.js` in this order:

1. `requestContext` — request id, `Permissions-Policy`, structured access log
2. `compression`
3. `helmet` — CSP with computed script hashes, HSTS in production, `frame-ancestors 'none'`, `no-referrer`
4. `cors` — **no origins allowed in production** (same-origin only)
5. `Cache-Control: no-store` on all `/api`
6. Rate limiting (classes below)
7. `originGuard` — CSRF defence on every state-changing method
8. Method allowlist → `405`; `Content-Encoding` rejection → `415`; non-JSON body → `415`
9. `validateEnvelope` — strict Zod schema per query string; URL length cap → `414`
10. `express.json({ limit: '32kb', strict: true, inflate: false })` → `413`
11. `rejectDangerousKeys` — `__proto__`/`prototype`/`constructor`, control characters, depth > 8

## Rate-limit classes

Nine classes, not one limiter. **Durable** classes are backed by Firestore and
survive a restart; the rest use in-process counters. See `backend/security.js`
for why the split is drawn where it is.

| Class | Window | Limit | Durable | Applies to |
|---|---|---|---|---|
| `public` | 60s | 300 | no | all `/api`, except the authenticated dashboard routes (`/api/admin/*`, `/api/orders*`, `/api/menu/admin/*`), which have the classes below so a working admin is never throttled by the catalogue budget. `GET /api/admin/settings` and `GET /api/admin/session` are unauthenticated and stay on it. |
| `login` | 15min | 10 | **yes** | `POST /api/admin/session` |
| `checkout` | 10min | 20 | **yes** | `POST /api/orders` |
| `tracking` | 15min | 20 | **yes** | `/api/orders/track/*` |
| `coupon` | 15min | 20 | **yes** | `POST /api/admin/promos/validate` |
| `report` | 60s | 60 | no | `/api/orders/stats`, `/api/admin/users` |
| `book` | 60s | 120 | no | `/api/orders/book` (mostly bodiless 304s) |
| `admin-write` | 60s | 60 | **yes** | admin `PATCH`/`DELETE`, and `POST /api/menu/admin/*` |
| `otp-request` | 60min | 20 | **yes** | `POST /api/account/request-code` |
| `otp-verify` | 15min | 30 | **yes** | `POST /api/account/verify-code` |

All return `429 {"error":"RATE_LIMITED"}` with `RateLimit` draft-8 headers and
`Retry-After`.

| Method | Path | Auth | Input | Output | Datastore | Limit | Tested |
|---|---|---|---|---|---|---|---|
| GET | `/api/menu` | PUBLIC | — | categories with items, derived selling price | read `categories` (visible), `products` | public | boot, e2e |
| GET | `/api/menu/admin/products` | ADMIN | — | products + raw discount config | read `products` | report | security |
| POST | `/api/menu/admin/products` | ADMIN | `productCreate` | `{product}` 201 / 409 duplicate | `.create()` `products` | admin-write | security |
| PATCH | `/api/menu/admin/products/:id` | ADMIN | `productPatch` | `{product}` | update `products` (closed field list) | admin-write | security |
| DELETE | `/api/menu/admin/products/:id` | ADMIN | — | 204 / 404 | delete `products` | admin-write | security |
| GET | `/api/menu/admin/categories` | ADMIN | — | `{categories}` | read `categories` | report | security |

| PATCH | `/api/menu/admin/categories/:id` | ADMIN | partial `categoryBody` | `{ok}` / 404 | update `categories` | admin-write | security |
| DELETE | `/api/menu/admin/categories/:id` | ADMIN | — | 204 / 409 not-empty / 404 | counts `products` first, then delete | admin-write | security |

`productCreate` bounds every string (name 200, description 2000, note 200) and
validates `image` against `^(?:|/img/[a-zA-Z0-9_-]+(?:@[12]x)?\.(jpg|jpeg|png|webp|avif))$`
— a path, never a URL, so `javascript:`, `data:` and absolute hosts are refused.

Discount configuration is validated **merged over the stored document**, which is
the only view where the real trap is visible: raising the discount today and
cutting the price tomorrow each pass alone, and together they sell at zero.

## Orders — `backend/routes/orders.js`

| Method | Path | Auth | Input | Output | Datastore | Limit | Tested |
|---|---|---|---|---|---|---|---|
| POST | `/api/orders` | PUBLIC | `checkoutBody` | `{order,duplicate}` 201/200 | **transaction**: 6 reads, then order + customer + promo + counter + idempotency | checkout | orderTransaction, security, e2e |
| GET | `/api/orders/track/:reference` | PUBLIC + phone | `?phone=` | redacted order + history | read `orders` | tracking | security, e2e |
| GET | `/api/orders` | ADMIN | `?page&perPage&status&q` | paginated | read mirror (fallback: indexed query / bounded scan) | public | security, e2e |
| GET | `/api/orders/book` | ADMIN | `If-None-Match` | `{orders,total,complete,limit}`, newest 3,000; **304** when unchanged | read mirror (fallback: count + ordered read) | book | mirror |
| GET | `/api/orders/stats` | ADMIN | `?days` | aggregates | 5 aggregation queries + 11 counts + 1 windowed read | report | boot, e2e |
| GET | `/api/orders/:reference` | ADMIN | — | order + history | direct get | public | boot |
| PATCH | `/api/orders/:reference/status` | ADMIN | `{status,note?}` | `{order}` / 409 | **transaction**: compare-and-set + history + audit | admin-write | boot, security |

**`checkoutBody` does not contain price, subtotal, discount, delivery or total.**
They are not optional-and-ignored — they are absent from the schema, so a client
sending them has them stripped before anything downstream could read one by
accident. `expectedTotal` is the single exception and can only cause a refusal
(`409 PRICE_CHANGED`, with the authoritative figure returned).

Tracking requires reference **and** phone, and returns one message for "no such
reference" and "wrong phone" alike — telling them apart would confirm which
references exist, and they are sequential by design. Contact details, address and
staff notes are stripped from the response.

| DELETE | `/api/admin/promos/:code` | ADMIN | — | 204 / 404 | delete `promos` | admin-write | security |
| POST | `/api/admin/promos/validate` | PUBLIC | `{code,subtotal}` | `{code,discount}` / 400 | read `promos` | **coupon** | e2e |
| GET | `/api/admin/settings` | PUBLIC | — | `{settings}` | read `settings/shop` | public | boot, e2e |
| PATCH | `/api/admin/settings` | ADMIN | partial | `{ok}` | merge `settings/shop` | admin-write | security |

The sign-in comparison is constant-time over SHA-256 digests of both sides, and
returns the same 401 shape for a malformed body and a wrong key.

**A promo's expiry is a day in Cairo.** The dashboard's date picker sends `expiresAt` as the
last millisecond of the chosen day in `Africa/Cairo` (UTC+3 in summer, UTC+2 in winter),
computed by `shared/cairoTime.mjs`; with no date it sends `null`, never an empty string. The
server stores that instant, refuses a date already past on create, and stops accepting the code
once it has passed. A code is letters, numbers, `-` and `_` only, and never `__name__`, because
it is the Firestore document id; anything else is `400 INVALID_PROMO`, never a server error.

`POST /api/admin/promos/validate` is public because checkout has to tell a
customer their code is good before they commit — but it returns **only the
discount**, never the promo's configuration, and the authoritative evaluation
still happens inside the order transaction. It is rate limited as `coupon`
specifically to make enumeration expensive.

`usedCount` is absent from the promo writable list: it is a redemption ledger,
incremented only inside the order transaction.

## Customer accounts — `backend/routes/account.js`

| Method | Path | Auth | Input | Output | Datastore | Limit | Tested |
|---|---|---|---|---|---|---|---|
| POST | `/api/account/request-code` | PUBLIC | `{email,lang?}` | `{ok,delivered,via}` / 429 | **transaction** on `otpCodes` | otp-request + per-address quota | security, e2e |
| POST | `/api/account/verify-code` | PUBLIC | `{email,code}` | `{customer,linkedOrders}` / 400 | **transaction**, then `claimProfile` transaction | otp-verify | security, e2e |
| POST | `/api/account/signout` | PUBLIC | — | `{ok}` | delete `sessions` | public | security |
| GET | `/api/account/me` | PUBLIC | — | `{customer\|null,mailConfigured}` | read `sessions` + `profiles` | public | e2e |
| PATCH | `/api/account/profile` | CUSTOMER | 4 bounded strings | `{customer}` | merge `profiles` (closed list) | public | security |
| GET | `/api/account/orders` | CUSTOMER | — | `{orders}` | `where profileId ==` | public | security |

Two independent quotas on code requests: a per-IP limiter stops one machine
walking many addresses, and a per-address quota (3/hour, 5/day, 60s cooldown)
stops one mailbox being flooded.

`GET /api/account/orders` is keyed on `profileId`, **not** on the email field.
Keying on email would make history readable by anyone holding a session for an
address, including one typed at checkout and never verified.

`GET /api/account/me` answers for anonymous visitors with `customer: null` rather
than 401, because every page asks it on load.

## Routes deliberately absent

Verified 404 by `tests/security/security.test.js`:

`/api/debug`, `/api/test`, `/api/payments`, `/api/webhook`, `/api/seed`

No payment or webhook endpoint exists. Holland Cookie is cash-on-delivery only;
`backend/orderTransaction.js` rejects any non-cash method with
`400 PAYMENT_UNAVAILABLE`. Adding a provider means adding those routes, with
HMAC verification and idempotent callback handling, as a separate piece of work.

There is no seed endpoint. Seeding is `node backend/seed.js`, run deliberately.
